## Why

Staff currently land on one unified `Dashboard.jsx` that branches internally per role and shows only data staff already know how to look up (counts, tables, low-stock lists). None of the ML models the project already trains (disease risk, revenue forecasting, inventory demand) surface anywhere until a staff member thinks to ask the AI chat assistant. Landing on the dashboard is a natural moment to proactively hand each role the one or two things worth their attention that day, without them having to know a model exists or phrase a chat question to reach it.

## What Changes

- Split the single `client/src/pages/Dashboard.jsx` (role-branching via inline `user?.role === ...` conditionals) into three distinct components: `AdminDashboard.jsx`, `VetDashboard.jsx`, `ReceptionistDashboard.jsx`, each rendering only its own role's stat cards, quick actions, and tables. `/dashboard` routes to the correct one based on `req.user`/`user.role`; shared layout/data-fetching logic is extracted into a common hook/util rather than duplicated three times.
- Add an **AI Daily Briefing** card to each of the three dashboards: a short natural-language summary plus 2-4 bullet insights, generated by aggregating existing trained ML model outputs (no new model training) and passing them through the existing Ollama LLM client for summarization — the same generation path RAG already uses, invoked directly rather than through the RAG retrieval/chat pipeline.
  - **Admin**: revenue forecast trend, top revenue services, inventory reorder-alert count, disease outbreak/pandemic risk level.
  - **Veterinarian**: today's scheduled appointments cross-referenced against pet-level disease-recurrence/cancer risk, plus a clinical disease-trend note. No pandemic-risk figure (stays admin-only, unchanged from current RAG behavior).
  - **Receptionist**: inventory reorder suggestions and a schedule/billing operational summary (today's appointment load, outstanding balances). No clinical/disease data, matching the existing role boundary.
- New backend endpoint(s) (e.g. `GET /api/ml/briefing` in `server/src/routes/mlRoutes.js`, branching on `req.user.role`, or one route per role) that call the existing ML proxy functions in `mlService.js` server-side, assemble the role-appropriate payload, and call the LLM summarization step. Each route/branch gets explicit `authorize(...)` role gating — no relying on the frontend to hide role-inappropriate content.
- **BREAKING (internal only)**: `client/src/pages/Dashboard.jsx` is removed/replaced; anything importing it directly (none found outside routing) must be updated. No public API contract changes.
- As a closely related fix (touches the same code path this change adds authorization to): add `authorize('veterinarian', 'admin')` to the existing `POST /api/ml/disease/pet-risk`, `POST /api/ml/disease/cancer-risk`, and `GET /api/ml/disease/pandemic-risk` routes in `server/src/routes/mlRoutes.js`, which today only require `authenticate` despite doc comments claiming "vet+admin" — currently any authenticated staff role, including receptionist, can call them directly.

## Capabilities

### New Capabilities
- `staff-dashboards`: role-specific dashboard rendering — three distinct dashboard components (admin, veterinarian, receptionist), each showing only its own role's data and quick actions, replacing the single conditionally-rendered `Dashboard.jsx`.
- `ai-daily-briefing`: an AI-generated, role-scoped summary card shown on each staff dashboard, aggregating existing ML model outputs into a short natural-language briefing without new model training, gated server-side by role.

### Modified Capabilities
(none — no existing `openspec/specs/` capabilities exist yet in this project)

## Impact

- **Frontend**: `client/src/pages/Dashboard.jsx` removed; new `client/src/pages/AdminDashboard.jsx`, `VetDashboard.jsx`, `ReceptionistDashboard.jsx`; new `client/src/components/AiDailyBriefing.jsx` card; `client/src/App.jsx` routing updated; a new `client/src/services/*` function to call the briefing endpoint(s).
- **Backend**: `server/src/routes/mlRoutes.js` (new briefing route(s) + authorize fix on the three pre-existing routes), `server/src/controllers/mlController.js` (new briefing handler(s) aggregating calls to `mlService.js`), possibly a small new `server/src/services/briefingService.js` to keep aggregation logic out of the controller.
- **ML service**: no new model training. Reuses `ml/scripts/rag/ollama_client.py`'s generation call directly for summarization; existing `/api/ml/sales/*`, `/api/ml/inventory/*`, `/api/ml/disease/*` routes are called, not modified in `ml/app.py`.
- **Dependencies**: adds a runtime dependency on Ollama being available at dashboard-load time (degrades gracefully to "insights unavailable" per CLAUDE.md's existing pattern for AI unavailability, not an error state).
- **Performance**: each briefing call fans out to 2-4 ML endpoints plus one LLM generation call; design.md must resolve caching/cadence (e.g., cache per user per day) to avoid a slow synchronous chain on every dashboard load.
